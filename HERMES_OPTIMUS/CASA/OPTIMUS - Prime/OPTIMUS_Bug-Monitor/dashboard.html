Bug documentation — the ghost path (C:\c\Users\...)

1. What it is

A ghost path is a POSIX/MSYS-spelled absolute path — /c/Users/apviz/AppData/Local — consumed by native Windows code. On Windows that string is rooted (Path.is_absolute() returns True) but carries no drive. Every filesystem operation beneath it therefore resolves against whatever drive happens to be current, which on this machine is C:. The result is a duplicated-drive tree: 

C:\c\Users\apviz\AppData\Local\hermes\...      <-- 4.7 GB, 107,334 files

Windows forbids a colon in a path component, so the literal C:\C\Users spelling can never be created. The lowercase C:\c\ form is the only possible artefact, and the monitor probes for it.

2. Where the error came from

Not a typo. The operator's hypothesis was “an added C/, probably caused by a missing : in a command line.” The mechanism is close but different: a value was authored correctly and then transcribed in MSYS spelling by a shell, and later trusted verbatim by Windows code.

The poisoned value was TELEGRAM_AGENT_HOME=/c/Users/apviz/.telegram-agent.

  • It appears in every archived config going back to at least 2026-09-17 — 131 files inside the HERMES_BACKUP restore point alone, and 135 more across state-snapshots, backups/config and *.bak in the live install.
  • It is not a path Hermes invented. It is a path somebody wrote while working in Git Bash / MSYS, where /c/Users/... is the correct and normal spelling.

3. The source-level defect

hermes_constants.py built the Windows home with no drive validation: 

local_appdata = os.environ.get("LOCALAPPDATA", "").strip()
base = Path(local_appdata) if local_appdata else Path.home() / "AppData" / "Local"
return base / ("hermes" + suffix)

Three call sites carried the identical pattern — all now fixed:

FileFunctionConsequence when poisoned
hermes_constants.py_get_platform_default_hermes_homeCreates the whole C:\c\ tree
hermes_state_guard.py_real_platform_state_rootGuards live state.db against a path that does not exist — isolation silently disarmed
hermes_cli/dashboard_procs.pyprocess home resolutionDashboard identifies processes against a phantom home

Two further guards were added in hermes_cli/_launchers.py as defence in depth: refuse to mkdir a drive-less directory, and refuse to persist one into the user PATH.

Hermes already shipped the correct primitive — tools/environments/local.py::_msys_to_windows_path() converts /c/Users/x to <WIN_HOME>\x. It was simply not applied to LOCALAPPDATA. The new has_drive() validator rejects drive-less values rather than normalising them, because guessing at intent is how the ghost was born.

4. Blast radius — why it was classed as critical

  • 4.7 GB / 107,334 files of duplicate install tree.
  • Both installs claimed the same install key (c5fcaaf047e746c6), so the ghost was corrupting real package-manager state.
  • A 0-byte state.db and a second SQLite writer on the same logical database — the reported "state.db is corrupted after update: cannot read header".
  • A drive-less entry was written into the user PATH (\c\Users\apviz\AppData\Local\hermes\bin), shadowing the real launcher for every subsequent shell.

Why the guard is a source edit and not an env var: setting HERMES_HOME would steer get_hermes_home(), but _get_platform_default_hermes_home() is still consulted directly at hermes_constants.py:90 and :219, and by the two other carriers. A corrected environment variable reduces exposure; only the source guard removes the defect.

6. Cleanup policy — what was rewritten and what was deliberately preserved

“Make the path vanish forever” and “document the error in depth” are in direct tension for files that mention the bug. The resolution used:

ClassActionReasoning
Live config (.env, config.yaml, .ps1, profiles) rewrittenRead at runtime; directly regenerates the tree.
Rollback-capable archives (state-snapshots, backups/, *.bak) rewrittenAn archive is only inert while nothing restores from it. A single rollback reinstates the poison.
HERMES_BACKUP restore point rewritten
in place, no files added		 Restricted by the operator to ghost-path fixes only, so no backup files were written into it. The change is a deterministic string swap and therefore reversible by hand.
.curator_backups\blobs\*preserved These are the documents that explain the MSYS pitfall (“git -C /c/Users/... fails in MSYS2 bash. Use native paths”). Rewriting them makes the warning unrecognisable and destroys the knowledge.
sessions\request_dump_*.jsonpreserved Historical transcripts. Inert; rewriting them would falsify the record.

Note on the historical value. The restore point consistently wanted /c/Users/apviz/.telegram-agent, i.e. the user profile root. That was the original intent, but the populated, credential-bearing, currently-configured directory is the Hermes-managed one. The /c/ prefix was never a different destination — it was the same path written in the wrong dialect. The SOT follows the live system, not the spelling.

8. Open findings — reported, not fixed

  • creds.json in the WhatsApp SOT is 0 bytes (2026-09-22). Worth confirming whether WhatsApp is genuinely authenticated or silently re-pairing.
  • The Hermes checkout is dirty: 204 files with real content changes and 64 with line-ending-only changes versus 105e876586. This is why the version string reads .dirty. Left untouched — it is accumulated local state, not a defect.
  • Five plaintext secrets remain in scripts/messaging_startup_full_env.ps1 and are duplicated across .env, config.yaml and the profile configs. Not rotated — rotation would break the live bots and was not authorised.

9. Extending this monitor

The system was deliberately built to absorb more defect classes. To add one, add a probe_*() function, fold it into probe()'s return dict, extend _state_key() with its identity, and add a section to build_report(). The cadence, ring buffer, popup, dashboard and runbook need no changes.
